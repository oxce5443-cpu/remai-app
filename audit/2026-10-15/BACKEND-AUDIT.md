# Backend readiness audit — 2026-10-15

Verdict: **NOT READY for public transactions**. This is a local source and isolated-test audit, not a cloud deployment or merchant certification. No production functions, databases, payments, configuration, or credentials were changed. Paths below are relative to the project root; `CF` means `小程序前端/uniCloud-aliyun/cloudfunctions`.

## Verified architecture

- Fifteen first-party cloud functions cover identity, public catalogue/store/banner reads, customer cart/address/orders/member/benefits, payment, administrator operations, QR codes and explicitly gated seeding.
- Customer authenticated functions validate `uni-id-common` tokens and derive ownership from the verified UID. Administrator H5 calls `admin` through `管理后台/src/utils/api.js:35`; all non-login actions pass `checkAdminAuth` (`CF/admin/index.js:620`). Legacy distributed admin mutation actions are rejected before database access.
- Payment callbacks verify signatures and merchant/app/currency/amount before settlement. Settlement uses database transactions, deterministic ledger identifiers and an order settlement marker (`CF/pay/index.js:68-118`). This is a useful safeguard; it does not solve creation consistency or externally collected money requiring compensation.
- Seventeen schema files exist. Local tests assert server-owned writes are denied to clients and sensitive identity fields cannot be read. Deployed schema state remains unverified.

## Bilingual data and error contracts

English UI text alone cannot translate merchant-authored product/category names, descriptions, store notices, coupons, selected spec names or historical order snapshots. Current admin `addGoods`/`updateGoods` destructure only Chinese-oriented single-value fields (`CF/admin/index.js:281-299`), so merely adding a client English input would be discarded by the server.

Use optional explicit translation fields while preserving original Chinese and stable IDs, e.g. `name_en`/`description_en` or a documented locale object. Carry them through schema, admin forms, writes, catalogue responses and order snapshots. Fall back to original merchant text when translation is absent; do not invent translated legal/business content. Existing historical records require safe read fallbacks, not bulk rewrites.

Cloud functions mostly return stable `errCode` plus Chinese `errMsg` (for example `CF/order/index.js:28-59`). Localise by code in a shared client error presenter; do not display raw server exception messages to customers. Dynamic details should be structured arguments such as product ID/name, not embedded Chinese sentence matching. `uni-id/index.js:138` forces `locale: 'zh-Hans'`; selected UI language should propagate through supported identity locale handling. Keep stored action names/statuses and monetary units unchanged.

## P0 atomic order creation batch

`order.createOrder` now requires `request_key` (16–128 ASCII letters/digits/underscore/hyphen). The client must persist one key and its exact checkout payload across request timeouts and app restarts until the order ID is recovered. An intentionally new checkout uses a new key. The server derives a 32-hex-character ID from SHA-256 of verified UID and key; duplicate IDs are protected by the database primary key. There is no expiry that could turn a late retry into a second chargeable order. The key itself is not stored in the order.

One transaction reads an existing owner-scoped order or reads current products, checks aggregate quantities, snapshots canonical product names/English names/images, calculates integer-cents totals, and inserts header plus all deterministic lines. New headers record `creation_complete`, `line_count`, `line_ids`, `lines_hash`, and a canonical request fingerprint. Replays verify ownership, matching payload, complete line manifest and hash before returning the original order/current status. Changed business payload with the same key fails `IDEMPOTENCY_CONFLICT`; missing/corrupt lines fail `ORDER_INCOMPLETE`. Generic SDK/transaction failures roll back and expose only `ORDER_CREATE_RETRY`, not raw SDK messages. The customer should retry with the same persisted key. Legacy order reads/payment paths remain available; no legacy data is rewritten and their pre-existing completeness is not certified by this change.

Eight additional tests exercise actual order function source against the transaction model: atomic complete/repeated creation, failure on the second line with rollback of header and the first line, concurrent duplicate then replay, payload conflict/owner separation, absent key/transaction support, corrupt manifest, replay after catalogue changes with explicit ownership rejection, and aggregate duplicate-product stock. Initial tests observed separate generated orders, missing conflict rejection and no key requirement before implementation. Combined backend/detail suite now **102 passed, 0 failed**; static plan remains **62/62**, source syntax and scoped whitespace checks pass. These tests do not verify actual cloud transaction API limits/isolation. New requests are bounded to 50 lines; real deployment concurrency/size limits and transaction dependency behaviour remain integration gates. No cloud operation or deployment occurred.

This batch closes the local nontransactional new-order creation path; it does not close merchant payment/refund/cancellation/QR or full-specification quotation defects. The main integration task owns the persistent customer checkout-key implementation and its relaunch/retry verification.

## P0 local cancellation race batch

Customer cancellation now conditionally updates the matching order ID, verified owner and `pending` status in one database operation. If payment won after the initial pending read, the paid status and stock flag are preserved and cancellation returns `ORDER_STATE_CHANGED`. Pending orders do not reserve stock, so this path no longer invokes inventory rollback; inconsistent legacy pending records already marked inventory-deducted or settled fail closed with `ORDER_RECONCILIATION_REQUIRED` for operator reconciliation. Normal pending cancellation still succeeds. Race and legacy-inconsistency regressions observed erroneous success before the change, then passed; combined backend/detail suite: **105/105 passed**.

This only fixes overwriting a locally committed payment. A merchant payment may still succeed after local cancellation because merchant close/query/refund/reconciliation remains absent. Such money is not refunded or reconciled by this change, and this release blocker remains open. No external merchant request was made.
